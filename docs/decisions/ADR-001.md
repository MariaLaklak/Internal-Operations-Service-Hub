# ADR-001: Use a Relational Data Model

## Status

Accepted

## Context

The Internal Operations Service Hub needs to store users, departments, requests, comments, approvals, and request history.

These pieces of information are connected. Each request belongs to one employee and one department. It can also have a responsible staff member, comments, an approval decision, and history records.

The data must stay consistent. For example, a comment must belong to an existing request, and a request cannot have more than one responsible staff member at a time.

The project must also be manageable within the five-week academy.

## Decision

I chose a relational data model for the application.

The main entities will be stored separately and connected using identifiers. For example, each comment will reference the request it belongs to and the user who wrote it.

This decision describes the storage approach. The specific database software will be chosen during implementation.

## Alternatives Considered

### Document-Based Storage

A document database could store a request together with related information.

However, users and departments are shared across many requests. I would need to decide carefully which information to reference and which information to duplicate.

For this project, a relational model gives me a clearer way to represent these connections.

## Reasons

- The main entities have clear relationships.
- Constraints can help prevent invalid references and duplicate assignments.
- The application needs to find requests by employee, department, staff member, and status.
- Related changes, such as a status update and its history record, can be saved together in a transaction.

## Consequences

The model will make it easier to connect information and apply consistency rules.

However, the relationships and constraints must be planned carefully. Later changes to the data structure may require database migrations.

A relational database does not replace authorization checks. The backend must still check the user's role, department, and request ownership.

## Related Requirements

This decision supports:

- Request ownership and department assignment.
- One responsible staff member per request.
- Comments linked to their author and request.
- Approval decisions and request history.
- Reliable storage of separate simultaneous requests.
